# 工程包契约:菜层 · 克重守恒 · 生熟形态 · 调味 · 自定义表新口径

> 2026-07-08 与用户逐条定稿。执行时按第六节顺序分步推进,每步先讲后做、配单测。
> 完成后将其中的持久性结论(表结构/查表优先级/输出结构)折叠回 CLAUDE.md 相应章节,本文件归档删除。

## 背景与动机(真实错例驱动)

1. **成分双重计算**:"毛毛虫面包120克,奶油占其中"被记成面包120g+奶油30g(150g 的热量)——输出结构里没有"菜"这一层,模型无处表达总量关系,代码无法校验;
2. **生熟不分**:"生米100克"被按熟米饭算——生熟差3倍热量,靠提示词叮嘱不可靠;
3. **调味缺失**:炒菜补了油,但糖/麻酱/沙拉酱类高热量调味没算;
4. **用户将批量收集食物数据**(每100克口径),现有自定义食物表按"份"设计且名字清单全量注入提示词,不可扩展——该捷径违反"禁止 prompt hack"铁律(CLAUDE.md 决策9),连根拔掉。

## 一、数据层(两次小迁移 + 一个预处理脚本)

1. **自定义食物表(user_foods)改口径**:存"每100克"的热量/蛋白/脂肪/碳水/纤维,与官方表同构;加"形态"字段(可空);"按份/unit"概念删除。现有一两条按份演示数据手工处理。批量灌数据=用户写脚本直插数据库,不做导入接口。表仍按用户隔离(单人期无感,多用户再议);
2. **官方表(food.json)预处理升级**:每条打"形态"标签(生/熟/干/水发/即食,脚本按命名规则打+人工抽查);同一基础食物的不同形态建"歧义簇"(米簇={稻米(生)、米饭(蒸)…}、面条簇、木耳簇等);
3. **食物记录表(food_records)加可空"所属菜名"标签**:同一道菜的成分带同名标签。**不建菜表**——菜不是实体,菜合计展示时现算。

## 二、解析输出结构(模型只做提取)

1. 每条食物带:**原话叫法**(用户嘴里的词,照抄,代码用它查自定义表)+ **标准名映射**(往官方表靠,原逻辑)+ **克数** + **形态**(明说才填,没说留空不许猜)+ 明说餐次 meal_slot(已上线,不变);**units 份数字段删除**;
2. **拆解类输出为"一道菜"**:菜名 + 总克重 + 成分清单(每成分=名字+克数+形态);单独报的食物不带菜结构;
3. **"记住"新口径**:必须能换算成每100克——用户给"克数+热量",代码算每100克入库;
4. **提示词删除两处**:自定义食物名字清单注入(整段);"按份填份数"规则。**新增两处**(正当语言职责):拆解时糖/芝麻酱/沙拉酱/蚝油等高热量调味显式成条、可删可改(盐/醋/酱油忽略);"勺/碗"等个人单位靠用户记忆("一勺=30克")换算成克。

## 三、硬校验(微循环新增三条,代码当裁判)

1. **克重守恒**:菜的成分克数之和=总克重,容差±5%;超差带差额打回重拆,重试不过→降级为整体估算一条并标 llm_estimated;
2. **形态裁决**:查表命中歧义簇且形态为空→不猜,簇内条目作封闭候选,连用户原话交模型二选一(现有候选重映射机制的延伸);
3. **"记住"缺克数→打回**,回执提示补克数。

## 四、查表优先级(修订)

> 用户自报 > **自定义表**(原话叫法精确命中;数据库+内存缓存,支持数千条)> 官方表(标准名+形态联合命中)> LLM 估算

自定义表同时参加候选召回(叫法相近也可被召回让模型裁决)。

## 五、展示(/days,向后兼容)

- 餐次 items 分两种:**菜**(菜名+总克重+合计热量+成分列表)与**单品**(现有格式原样);
- 老数据无菜标签→全部按单品平铺,零迁移天然兼容;
- 前端三层:餐次→菜/单品→成分;成分与单品照旧可改可删(复用现有抽屉),改删后所在顿重算,菜合计现算无需维护;
- 展示口径对数据来源(官方表/用户收集)无感知。

## 六、顺序与验收

迁移 → 预处理脚本(形态+簇)→ 解析结构+硬校验 → 查表 → 展示接口 → 前端。每步配 pytest 单测(中文名),做完跑全套并贴真实输出。

**真机验收四案**:①毛毛虫面包复测(克重守恒);②生米 vs 米饭(形态裁决);③新口径"记住";④脚本灌几条数据后查表命中。

**明确不做**:菜表实体、导入接口、形态标签全表完美化(高频类目优先,长尾走候选裁决兜底)。
